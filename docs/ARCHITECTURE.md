# YAMV — architecture

YAMV is a markdown viewer for Windows and macOS. `Yamv.Core` holds every piece of logic that can run without a UI (grouping, session, single-instance, rendering markdown to HTML); `Yamv.App` is the Avalonia 12 shell around a `NativeWebView`. Core references no UI framework. Terms are in the [glossary](glossary.md).

## Layers

- **`Yamv.Core`** (`src/Yamv.Core/`): owns grouping, git-root discovery, the session file, the single-instance lock and pipe, launch-argument parsing and markdown → HTML. References Markdig and the BCL only; never Avalonia.

  One main instance per user is held by a lock file (flock on Unix) plus a named pipe (a socket file on Unix) derived from the lock path, which later launches signal over; a named mutex is not used, because its behaviour differs on macOS.

  Session saving (`Session/`): `SessionSaver` writes `session.json` through `SessionStore` 500 ms after a change (a `Debouncer`, so two saves never run at once) and at once on `Flush`; a failed save is logged and retried by the next.

  Logging (`Diagnostics/`): `IAppLog` is the app's log and `FileAppLog` writes it to a file. `LogText.Clean` replaces control, format, line and paragraph separator characters and unpaired surrogates with U+FFFD. A value taken from a document, a link, a file name or an external program is cleaned where it is put into a log line (the link, page-message and file-action sites), and `FileAppLog.Write` cleans every message again as a backstop and writes an exception's text line by line, each line cleaned and indented four spaces, so such text can never forge or split a log line.

  `WindowPlacement` picks the screen (`ScreenArea`) a saved rectangle overlaps most, in physical pixels, and clamps the rectangle there, so the client plus its visible outline sit inside the area as Windows' snap places a window; `WindowBounds.Scaling` is the screen scale it was saved at, and `Fit` takes a `WindowFrame` per scaling (`WindowFrame.None` is no frame). `Input/Shortcuts` matches a key to a `ShortcutCommand` (Ctrl/Cmd+W, Ctrl+Tab, Ctrl+Shift+Tab, Ctrl/Cmd+B, Ctrl/Cmd+R, Ctrl/Cmd+O, Ctrl/Cmd+[ and ], which step the width narrower and wider, and Ctrl/Cmd+, which opens the theme settings window).

  Documents (`Documents/`): `ReadFailure` turns an exception from reading a document into a reason (access denied for `UnauthorizedAccessException`, in use for an `IOException` whose `HResult & 0xFFFF` is 32 or 33, else a generic one) for the can't-read pane. `DocumentFileTypes` is the one list of in-app document types (`.md`, `.markdown`, `.mdx`, `.txt`; `Extensions`, `Patterns` for the pickers, `IsDocument`, case-insensitive), shared by the pickers, drag-drop and links. `DropHint` is the refusal text naming every extension, and `Sort(paths)` splits dropped paths into `DroppedFiles` (the documents in drop order, and a count of the rest; a folder is never a document, and it reads the disk).

  `DocumentFileWatcher` is [live reload](glossary.md)'s Core half: `SetPaths(documentPaths)` replaces the open documents (full paths, made canonical), and it raises `Changed` with a `DocumentsChangedEventArgs` of the open documents that may have changed, on a thread-pool thread, once the events naming an open document have been quiet for 150 ms or at most 1 s after the first.

  A subscriber posts to its UI thread and never waits on it there, since `Dispose` waits for a `Changed` already running; a subscriber that throws is logged. Each document window's view model subscribes through the App's `IDocumentChanges` seam (see Layers, App).

  Each folder of an open document is watched once, through the `IFolderEvents` and `IFolderProbe` seams of `Theming/FolderEvents.cs` that `ThemeFolderWatcher` shares. All work on a folder (probe, start and dispose its watch, read stamps) is that folder's pass on the thread pool, one pass per folder at a time, so a hung share delays no other folder; `SetPaths`, the 2 s tick and the watch's events only ask for a pass.

  Every 2 s a folder is probed: one that does not exist is watched once it does, and one deleted, recreated, replaced or whose watch reports an error is watched again, reporting every open document in it when it appeared, was replaced or the watch had worked before it failed.

  A folder whose watch cannot be started, or fails before it has worked for a full tick, is polled instead: every 2 s `FileStamps.Read` takes each open document's length and last write time (no document is opened), and only a document whose stamp changed since the previous poll is reported, so a rewrite that keeps both is missed.

  A document's first stamp is taken on a pass asked for when it is opened in a polled folder or the folder starts being polled; a change before that read is not reported. That window is one thread-pool dispatch (plus the rest of the folder's running pass), and, outside the watcher, the time between the subscriber's own read of the document and its call to `SetPaths`, so a subscriber reads a document and calls `SetPaths` close together (the [first-stamp window](glossary.md)).

  Links (`Links/`): `LinkPolicy.Decide(Uri?, LinkContext)` returns a `LinkDecision`: `OpenExternal(Uri, DroppedFields)`, `OpenDocument(Path, LinkPath, Fragment)`, `OpenWithDefaultApp(Path)`, `Confirm(Path)` or `Ignore(Kind, Reason)`. `Kind` is an [ignore kind](glossary.md) (`IgnoreKind`: `Scheme`, `NetworkShare`, `NotPlainPath`, `Missing`, `OutsideRoot`, `TrailingDotOrSpace`) the app words for the user, and `Reason` is the log line.

  A consumer hands the OS `OpenExternal.Uri.AbsoluteUri`, never `ToString()`, which unescapes `%26`; a `mailto` URI keeps only its address and the `to`, `cc`, `bcc`, `subject` and `body` fields, and `DroppedFields` names the rest. `LinkContext` carries the `GroupRoot` and a `Resolve` function (`RealPath.Resolve` in production).

  `LinkIo` is the one door to string and file-system queries on a path for `RealPath` and `LinkPolicy`: every full-path normalisation and every `FileInfo` construction goes through it and reports its input to a `touching` / `normalising` hook first, which tests use to prove no path is touched before the share and device check.

  On Windows `LinkIo.FullPath` calls `GetFullPathNameW` directly, a string operation that reads no disk or share, and never `Path.GetFullPath`, whose `~` short-name expansion would follow a link in the middle of a path to a share; short names stay as written there.

  `Decide` first ignores other schemes and `file:` with a host, then, on the raw path and before anything normalises or touches it, UNC and device paths and any path that is not fully qualified (on Windows, drive-rooted: a relative path or a root-relative `\x` is ignored).

  It then normalises through `LinkIo` and ignores names with a character no file name may hold (on Windows including `:`, for alternate streams), unresolvable paths, missing non-documents and anything outside the group root (compared exactly on resolved paths).

  On Windows it also refuses a real path with a segment ending in a dot or space (`TrailingDotOrSpace`), one Windows would rewrite (`NotPlainPath`), and a resolver result that is not local and fully qualified; `RealPath.IsNetworkShare` tells a share (`NetworkShare`) from a device path. A [viewable type](glossary.md) opens with the default app only when both the link's name and its resolved target are on `LinkPolicy.ViewableExtensions`; a folder or any other type asks first (`Confirm`).

  The App wiring of `LinkPolicy` follows these rules. `LinkActivatedEventArgs` carries a `Source` (`LinkSource`: `Click`, `Navigation`, `NewWindow`) and the `DocumentPath` shown when the link fired, and only a `Click` acts: a `Navigation` or `NewWindow` activation is logged and ignored. A drop is not a link: it is an Avalonia `Drop` on the window, or a `NewWindow` `file:` link that follows the page's drag signal (`LinkDropRoute`), and either skips `LinkPolicy`, so a dropped document opens wherever it is, with no group-root check, since a drop is the user's own gesture.

  The wiring opens, watches and restores exactly the `Path` the decision carries (the resolved real path), never the raw href or a re-resolved one, because the file can be swapped between the decision and the open; `OpenDocument.LinkPath` (the link's normalised path, which may hold an 8.3 name as written) is for the title and tree label only.

  A `.md` link is an `OpenDocument` only when its real path is a document type too and not a folder, else it is a `Confirm(real path)` (or `Ignore` outside the group root). A `.md` link outside the document's group root opens in-app in its own group, and a missing one opens as a missing document.

  `RealPath.Resolve` returns a `ResolvedPath?` (`Path`, `Exists`, `IsDirectory`), null when the path cannot be resolved safely. It follows links one hop at a time (at most 40, `MaxLinkHops`), never touches a UNC or device path (`\\server\share`, `\\?\`, `\\.\` and `\??\`), and returns long, on-disk-cased names; short names are expanded during the walk, one folder at a time, not by normalising.

  A relative input path (or, on Windows, one with no drive) is unresolvable, checked with the share and device test on the raw path before any normalising.

  On Windows a link's target is read from the reparse point (`FSCTL_GET_REPARSE_POINT`, symlink and mount point tags), never `ResolveLinkTarget`: an absolute target is accepted only as `\??\X:\…`, so `\??\UNC\…`, `\??\Volume{…}` (a folder-mounted volume is not followed), `\??\GLOBALROOT\…` and any other form make the path unresolvable; a relative-flag target starting with a single `\` is rooted at the link's drive, any other relative target is joined to the link's folder, and one rooted any other way is unresolvable; other reparse tags are walked as plain entries.

  On macOS and Unix the `LinkTarget` string is used, absolute as is and relative joined to the link's folder. Mapped network drives and other reparse tags are out of scope.

  A path segment whose name matches more than one entry in its folder ignoring case, and none exactly (a case-sensitive folder), makes the whole path unresolvable (null, so `LinkPolicy` ignores the link), since the OS would pick an entry the path was not checked as; an exact match wins (`RealPath.ChooseMatch`).

  `DocumentView.RaiseLink` passes every link on as it came, a `file:` link with a host included, and `LinkPolicy` refuses it.

  Platform (`Platform/`): `RevealCommand` builds the Explorer or Finder process that reveals a path (a file selected, a folder opened, a missing path's nearest existing folder), BCL only so it is tested without a window. `ShellExtension.IsMissing(path)` says whether the Windows shell reads a path as having no extension (see `OpenConfirmed` below). `OpenFileCommand.For(path, isMac)` builds the process that opens a fully qualified `.json` path with the system's association (the Windows shell open, or `/usr/bin/open` on macOS) and throws for any other path.

  Theming (`Theming/`) parses theme files, resolves a theme for light or dark, builds its CSS (`ThemeCss`), and keeps the catalog of built-in and user themes (`ThemeCatalog`: list, import, inspect, export, duplicate, rename, save, delete); the editing services are `ThemeEditing` (set or reset a token, add a half, rename), `ThemeTokenView` (the rows of one tab with value, layer and whether set there) and `ThemeFilePatch` (a save that edits only the changed values in the file's text).

  `ColorMath` and `Hsv` convert between HSV, RGBA and `ColorValue` for the colour picker; a grey keeps the hue the caller passes.

  Deleting goes through `IFileTrash`, which the App implements with `Platform/PlatformTrash` (the Windows Recycle Bin or the macOS Trash). `ThemeFolderWatcher` watches the user themes folder and raises `Changed` once per quiet 300 ms on a pool thread; a 2 s tick re-checks the folder, re-arms after an error and follows the folder being deleted or recreated. Theming owns no UI.

  Widths (`Widths/`) holds the content-width value (`ContentWidth`: px or Full, snapped to a 40 px grid; `TextSpace(paneWidth)` is the pane less the page's two 44 px side paddings, `SidePaddingPx` = 88, and every step compares against it; the pane is the document column's bounds less the scrollbar inset recorded from the page's last `IDocumentSurface.ViewportWidth`, or the whole column while that is null).

  `WidthScopes.For` lists the popover's Saved for segments from a document, its group root and the width's source, without touching the file system, and carries the caption, Reset and Clear all rules (`InheritedFrom`, `CanReset`, `ClearAllRoot`) and whether a width set on the selected segment reaches the document (`Reaches`).

  `WidthStore` holds the per-folder widths in `AppPaths.WidthsFile` (`widths.json`) shared by every instance: a lookup (`Resolve` by document path, `ResolveFolder` by folder) walks from the document's folder up to the file-system root, else the [app default](glossary.md); `CountAtOrBelow(groupRoot)` counts the folders `ClearAtOrBelow` would remove; changes are replaced atomically and the store's lock is held through file IO, so callers keep changes off the UI thread.

  Settings (`Settings/`): `SettingsStore` holds the app-wide theme id and Appearance in `AppPaths.SettingsFile` (`settings.json`), shared by every process: `Load` reads the file again on each call and keeps the settings read before when it is missing, locked or unparseable, and `SetThemeId` and `SetAppearance` change a fresh read and replace the file in one move (a failure is logged and returns false; an unparseable file is first copied to `settings.json.bad`).

  `SettingsWriter` saves the picks off the caller's thread: `Request(themeId, appearance)` records the pair and returns with no file IO, one background write at a time saves the latest pair through the store (picks that arrive meanwhile coalesce into one more write, latest wins), and a failed write is logged and the next request writes again. `WhenIdle()` completes once every pair requested so far is written or failed; `Dispose` stops taking requests and waits up to 2 s.

  `SettingsWatcher` watches `settings.json` (through `DocumentFileWatcher`) and raises `Changed` on a thread-pool thread with the settings the file holds after a change, whether made by hand, by another YAMV process or by this one's writer. A change seen while the writer is saving is not read at once: the watcher waits, holding no thread, for `WhenIdle()`, then re-reads and reports once however many changes came in meanwhile.

  A file that is missing, locked or unparseable reports the settings read before. Every change is reported, even one that leaves the values as they were; telling it apart from what is applied is the subscriber's job. A failure reading the file or reporting it is logged. `Dispose` waits for a `Changed` already running.

  Startup (`Launch/`): `LaunchOptions.Parse(args, currentDirectory, directoryExists)` turns the command line into a `LaunchRequest` (a folder argument is an `InvalidLaunch`, "Not a file: {path}"; a nonexistent path is kept), and `StartupPlan.Decide` turns that into a `StartupAction` (print and exit, register, unregister, or `StartApplication(Files)`, where empty files mean a main launch); `StartupPlan.FromResult`, `FromException` and `FromUnknownPath` turn a registration outcome into the line, stream, exit code and whether to notify the shell.

  Second launch (`Launch/SecondLaunch`): `SecondLaunch.RunAsync(requestDeadline, noPidDeadline, overallCap)` takes its effects as `SecondLaunchActions` (read pid, allow foreground, request, bring forward, retry the lock, delay, time) and returns a `SecondLaunchResult`.

  Its `Outcome` is `Activated` (exit 0, only when the app answered `opened`), `Failed` (exit 1: `Refused`, `NotResponding` or `Denied`, whether or not the launcher brought the window forward itself) or `BecameMain` (the lock came free within `LockWaitTimeout`, so the caller starts as the main instance).

  Each `activate` waits `RequestDeadline` (3 s) with a known pid or `NoPidDeadline` (1.5 s) without one, cut to what is left of `OverallCap` (8 s). An app that does not answer has its window raised from the launcher within `BringForwardBound` (1 s), then the launch waits for the lock or a new app's pid, and still exits 1 within the cap with no late raise; a `closing` reply waits the same way without raising.

  `InstanceCoordinator.TryAcquireMainLockQuietly` reports a `MainLockAttempt`.

  Open message (`Instance/`, `Launch/SecondLaunch`): the server hands each frame to its handler as an `InstanceRequest` (`Message`, `TryBegin`, `Complete(InstanceReply)`); every message, `activate` included, keeps its connection open for one reply (`Opened`, `Refused` or `Closing`, written as a frame), tracked, watched for hang-up and under the reply bound. An `open`'s `Opened` means the app took it and is opening it; an `activate`'s means a window came forward.

  `OpenMessage.TryEncode` / `TryDecode` turn a list of full paths into `open ` plus a JSON array and back (`OpenMessageProblem`: empty, not a full path, not well-formed text, over the 64 KiB frame); `InstanceCoordinator.RequestAsync` sends a message and waits for the reply as an `InstanceRequestOutcome`, for both `open` and `activate`.

  `SecondLaunch.OpenAsync(files, openDeadline, overallCap)` (the app passes `RequestDeadline`, 3 s per request, and `OverallCap`, 8 s for the whole launch) returns `Opened`, `BecameMain` (the app exited and the lock was taken, within `LockWaitTimeout`) or `Failed` with a `SecondLaunchFailure`: `Unsendable` (nothing sent: a payload over the 64 KiB frame cap is refused and never split, and a file name with a lone surrogate is `Unsendable` by design), `Refused`, `NotResponding` or `Denied`.

  A `closing` reply or a missing server with no pid waits for the lock or a new app's pid and sends again.

  `Program` (`RunSecondLaunch`) runs `RunAsync` for a no-file launch and `OpenAsync` for a launch with files, when it did not get the lock: `Activated` or `Opened` exits 0, a no-file `Failed` logs "Second launch: no window was brought forward (<Failure>); exiting 1." and exits 1, `BecameMain` runs as the app, a `Failed` logs "Second launch: the N file(s) were not opened (<Failure>); exiting 1." and exits 1 (no visible error yet).

  Launch arbitration (`Launch/LaunchArbiter`): a state machine driven from the UI thread that turns framework, file-open and Dock or `activate` events into the windows to open. `Start(files)` is the start the App uses: files open a viewer window, none the main window, with no grace timer; `MainWindowOpen` says whether it counts the main window as open.

  For a macOS cold start the grace path (`FrameworkReady`, `GraceElapsed`, `FilesOpened`, `Reopen`) waits `GracePeriod` (300 ms) after framework initialization for launch-time file events, so a Finder-opened file starts only a viewer window; the arbiter keeps no timer, it asks the caller to start one (`StartGraceTimer`) and hear back through `GraceElapsed`. Inputs in an order it does not cover return `None` and never throw.

  Only `Start`, `ActivateRequested`, `MainWindowOpened` and `MainWindowClosed` are wired in the App; these are the rules the grace path's wiring follows. A Dock click or `activate` during the grace is held, and the grace's end opens the main window even if files arrived in it.

  Files that arrive before `FrameworkReady` count as grace files: a viewer window opens, and no main window unless a held activate or Dock click asks for it. The App reports `MainWindowClosed` on every path, a failure while building the window included, or the arbiter goes on believing the main window is open.

  UI readiness and the last window (`Launch/UiReadyLatch`, `Launch/AppLifetimePolicy`): `UiReadyLatch` holds every UI job posted from a pool thread (the `open` and the `activate` of an instance request, each its own job, never merged) until the App opens it as the last step of `OnFrameworkInitializationCompleted`, then releases them in arrival order; once open it passes jobs straight through.

  `AppLifetimePolicy(LastWindowBehavior)` is the last-window rule: `Quit` (Windows) or `KeepRunning` (macOS, which `Program` picks).

  `DocumentWindowGone(remaining)` answers `LastWindowStep.StopAndQuit` only for `Quit` with no document window left, `Exiting()` marks the app stopping and says whether the exit still has to run the stop, and `MayOpenWindows` is false once it is stopping (an `activate` then answers `closing`, logs "Activate: the app is closing; answered closing." and builds no window).

  On Windows the app then stops answering and posts one quit job (`desktop.Shutdown()`) that re-checks for a document window opened meanwhile; on macOS the process stays running with no window, an `activate` opens the main window with its session, Cmd+Q (or the app menu's Quit) quits, and the server stops answering only at exit.

  Registration (`Registration/`, Windows only) writes and removes YAMV's [Open with registration](glossary.md) under the current user's `Software\Classes`, against an injectable root key so tests use a temporary subkey; it never takes over the default handler and removes only what it added.

The theme windows pass null toasts and stay log-only.

    `OpenWithDefaultApp` opens a fully qualified `.json` path through Core's `OpenFileCommand`: on Windows the shell open is started and a refusal throws an `IOException`; on macOS `open` is waited for 2 s and a non-zero exit throws, while a run that outlives the wait is logged and left alone. The theme settings window's Edit as text calls it through `ThemeSettingsHost`.

    `OpenViewable(path)` is the link opener's door to the default app: it throws `ArgumentException` for anything that is not a fully qualified local file of a [viewable type](glossary.md) with no control character, and on Windows for a path not rooted at a drive letter, with a `:` after the root or a name ending in a dot or space; otherwise it starts the same open as `OpenWithDefaultApp`.

    `Services/LinkOpener` (`LinkOpener(ILinkDocuments, IToasts, IAppLog, LinkOpenerSeams)`) carries out a clicked link; `MainWindow` builds one over its view model and disposes it on close.

    Its seams are the browser (over `TopLevel.Launcher.LaunchUriAsync`), the window's current `IFileActions`, `LinkPolicy.Decide` and a runner over `Task.Run`. Only a `Click` acts. The group root comes from the clicked document (`ILinkDocuments.GroupRootOf(DocumentPath)`), `Decide` runs off the UI thread, as does the browser call (Avalonia's launcher starts the handler synchronously, so a slow one would freeze the window), and the newest click in a window wins.

    The actions: `OpenExternal` hands the browser `Uri.AbsoluteUri` inside the runner; `OpenDocument` opens the document in the same window (`DocumentWindowViewModel.OpenLinkedDocument`; a missing document becomes a missing row) and scrolls to its fragment on first show, while a link to the shown document only scrolls it, with no render. A link that resolves to the shown document under another spelling (through a junction or a symbolic link) is handed back with the shown document's own path, so it scrolls too instead of adding a row; a `subst` drive is not mapped.

    The other actions: `OpenWithDefaultApp` goes through `IFileActions.OpenViewable`; `Confirm` shows the [confirm card](glossary.md) (below) and opens nothing until the user answers Open, which goes through `IFileActions.OpenConfirmed`; an `Ignore` shows a toast of the text for its `IgnoreKind`.

    `OpenConfirmed(path, isDirectory)` is the door for the card's Open: it throws `ArgumentException` for anything that is not a fully qualified local path (same plain-path rules as `OpenViewable`, with no viewable-type check, so a folder or any file type passes); otherwise it starts the same open.

    On Windows a folder starts `%WINDIR%\explorer.exe` with no shell, and a file the shell reads as having no extension is refused when a same-named `.pif`, `.com`, `.exe`, `.bat`, `.cmd` or `.lnk` (`FileActions.ProgramExtensions`) sits beside it, because `ShellExecute` runs that [program twin](glossary.md) (measured with `foo` and `foo.cmd`; `foo.txt` with `foo.txt.cmd` is not hijacked). The shell's reading (`PathFindExtensionW`) is Core's `Platform/ShellExtension.IsMissing`: no dot in the final name, or an ASCII space after its last dot (`notes. md`); whether the extension is registered does not matter. On Windows the confirm card words such a name as a file with no type.

    The confirm card: `Core/Links/ConfirmText` words the title from the sanitised name and the body from the real path, whether it is a folder and whether the platform is a Mac; `LinkOpener` sanitises the name (`ToastValue.Plain`, the plain-text sibling of `Code`). `Confirm` carries `IsDirectory` from the policy, so the words and the open agree. `ViewModels/ConfirmCardViewModel` holds the words and the Open and Cancel answers.

    `Views/ConfirmCard` is the content of `MainWindow`'s `ConfirmPopup`, a native popup over the web view whose scrim is sized to the document pane, so the title bar and tree stay live.

    `LinkOpenerSeams.Confirm(title, body)` is the seam that shows the card and returns whether the user chose Open. Cancel has the focus, Esc and Enter cancel, Enter opens only with the focus on Open, and a click on the scrim does nothing. Esc or Enter with focus away from the card cancels it too: the window's key handler catches them, and while the card is up `MainWindow.UpdateConfirmPopup` tells the page (`SetCardOpenAsync`, `window.yamv.setCardOpen`) so a page with native focus swallows both and forwards them as `key` messages, which `OnKeyForwarded` answers by cancelling before any shortcut. A document switch, minimising, closing the window or a newer link click cancels it, and `LinkOpener` asks nothing when the document was left before the card could show.

    Open ignores the pointer for the system's double-click time after each show, so the second click of a double click on a link cannot land on it. On Open, `LinkOpener` decides the link again and opens only an unchanged `Confirm`: the check-to-open gap lasts as long as the card stands.

    `YAMV_DEV_CONFIRM_CARD=1` (read only when `YAMV_DATA_DIR` is set) opens the card for a sample `setup.ps1` once the first document shows.

    `Views/` holds `MainWindow` (custom title bar, `TitleBar`, and the tree sidebar on the right), `EmptyState`, `MissingDocumentPane` and `UnreadableDocumentPane`; `Views/ContentWidthPopover` is the content-width popover's content, shown in `MainWindow`'s native `Popup` anchored to the title bar's ⟷ button (the popup is a window of its own, so it sits over the web view, and `MainWindow` owns its dismissals).

    The title bar's ⋯ button opens `MorePopup`, another native popup of `MainWindow` with one item, "Theme settings…" (hint Ctrl+, or ⌘, on macOS); opening it closes the width popover and the other way round, and its item, Ctrl/Cmd+, and the dev hook all go through `MainWindow.RequestThemeSettings`, which raises `ThemeSettingsRequested`.

    Drops: `Views/MainWindow` handles Avalonia's drag events on itself and on the overlay. `DragEnter` reads the dragged files' local paths once per drag and judges them by file name, and `DragOver` reuses that verdict; Avalonia's `TryGetFiles` stats each path as it lists them, so a slow share costs that read, once, on the UI thread; a drag with no local paths shows the grey form. While hovering, the source is told `Copy` when the drag holds a document, else `None`, so a drag of only non-documents ends with the grey form and no drop. At a drop with paths it is told `Copy`.

    `Drop` reads the paths inside its handler. `OpenDropped` sorts them off the UI thread (`DocumentFileTypes.Sort`), opens the documents as one batch with the first selected (`DocumentWindowViewModel.Open`), shows the Refusal toast `DocumentFileTypes.DropHint` once when any path was refused, and brings the window forward.

    The title bar's folder button, first among its tools, runs the same Open files… action as Ctrl/Cmd+O.

    `ViewModels/DropOverlayViewModel` is the overlay's state (`Hidden`, `Undecided`, `Open`, `Refused`): the page's [drag signal](glossary.md) and the window's drag events each start or stop a 300 ms grace, since their enters and leaves do not pair, and its end hides the overlay. `Views/DropOverlay` is the content of `MainWindow`'s `DropPopup`, a native popup sized to the body below the title bar so it sits over the web view; opening it closes the width popover and the ⋯ menu.

    `LinkOpener` takes a `NewWindow` link to an absolute `file:` URI as a drop when `DragSignalledRecently` holds (up to 2 s, ended by the page's leave or the end of the drag), queues its path (a drop raises one link per file, and only the first of a batch needs the signal), and a 50 ms timer, restarted by each arrival, hands the batch to the window's `OpenDropped`; a drop after the window closed is logged and opens nothing. `YAMV_DEV_DROP_OVERLAY` (`ok` or `no`, read only when `YAMV_DATA_DIR` is set) shows an overlay form once the first document shows.

    `HarnessWindow` is the dev harness (the old document-view test window), opened instead of the main window when `YAMV_DEV_HARNESS=1`. `YAMV_DEV_WIDTH_POPOVER` (`1`, `clearall` or `folder`, read only when `YAMV_DATA_DIR` is set; another value fails at start) has the start window (main or viewer) open the popover once its first document shows; a viewer opened later by an `open` request does not.

    `YAMV_DATA_DIR`, when set and not empty, is the data directory for the session (`session.json`), widths (`widths.json`), settings (`settings.json`), lock, logs and themes on every platform (`AppPaths.DataDirectoryVariable`).
  - `Views/ThemeSettingsWindow` is the theme settings window: the theme list (Built-in and Yours), the selected theme's header, an Appearance choice and a footer, over `ViewModels/ThemeSettingsViewModel` (the list, the selection and a working copy that edits change until Save or Revert; selecting a valid theme applies it, an invalid one only shows its errors) and `ThemeRowViewModel` (one row: chip colours, inline rename, whether Rename and Delete are on).

    `Views/ThemeSettings/ImportNoticeDialog` is the in-window scrim modal behind `ConfirmImport`, a card for the `ThemeInspection` (its `FilePath` is the path shown) with the css warnings; `ThemeSettingsWindow.ConfirmImportAsync` hosts it beside the confirm and disables everything behind it; a close cancels it (see `ConfirmCloseAsync` below). Its safe box uses `YamvCodeBackground`, a chrome brush because `codeBackground` is a chrome token in Core's `ChromePalette`.

    The view model's `ReloadFromDisk` and `KeepMine` commands and `ChangedOnDisk`, `DiskBroken` and `DiskError` drive the disk-change bar (`DiskBar` in `ThemeSettingsWindow.axaml`), and `ThemeRowViewModel.IsMissing` marks a greyed missing row the view model keeps for a theme whose file is gone while that theme is in use or selected (both can be listed at once; [look.md](design/look.md), [themes.md](design/themes.md)).

    `ThemeSettingsWindow.ConfirmCloseAsync` is the close check the window's own close and the app's shutdown wait on: it cancels an open Import notice or confirm, then asks the unsaved confirm (Save, Discard, Cancel) while the theme has unsaved edits.

    `Services/ThemeSettingsHost` owns the app's one theme settings window (`App.ThemeSettingsHost`, created for a main or viewer start, none for a harness start; `App.ShowThemeSettings(owner)` is the way in: `App` subscribes each document window's `ThemeSettingsRequested` in `Track` and calls it, and a failure to open is logged and shown as the warning toast "Couldn't open the theme settings" in the window that asked).

    `Show(owner)` builds the window through `BuildWindow` over the bridge's requested theme and Appearance, owned by the viewer or main window that asked and shown `CenterOwner`, or activates the open one. While it is open, `ThemesReloaded` reaches the view model's `OnThemesChangedOnDisk` and `SyncInUse`, and so does a `RequestChanged` the window did not make.

    The window outlives its owner while another document window stays open: an owner's close arrives as the owned window's cancellable `Closing` with reason `OwnerWindowClosing`, and `ThemeSettingsWindow.OnClosing` then moves the window to the successor (`OwnerSuccessor`, which `Create` takes as `ownerSuccessor` and `BuildWindow` sets; `App.SuccessorOf` names the most recently active other tracked document window, a non-minimised one first), with its unsaved edits and any open confirm or Import notice, and the owner's close goes ahead.

    With no other document window the window closes with its owner: cancelling its `Closing` cancels the owner's close, and while the theme has unsaved edits it waits on its Save/Discard/Cancel confirm and, after Save or Discard, closes the owner again.

    If the window moves while that confirm is open, Save or Discard leaves it open over its new owner, clean, and closes no window. An app or OS shutdown's close never moves it.

    `App.OnShutdownRequested(e, tryShutdown)` asks the host's `ConfirmShutdownAsync` (the window's `ConfirmCloseAsync`) before quitting: a pending check holds the shutdown, asks for it again once it passes, and starts no second check for a repeated request; Cancel, a failed save, or a check that throws (logged) keeps the app running. `Dispose` closes the window without the confirm (`ForceClose`).

    `Views/ThemeSettings/TokenEditor` is the token editor (a row per token, the Light/Dark/Shared tabs and, on a one-half theme, the "This theme has no dark half" strip with its Add dark button), over `TokenRowViewModel` (one row's shown value, commit, reset and error) and the view model's token rows, tab state and `Hint`; a swatch raises `PickRequested` with `TokenPickEventArgs` and, on an editable row, opens `Views/ThemeSettings/ColorPickerPopup` (an overlay-layer Popup inside `TokenEditor`: saturation/value square, hue and alpha bars, old and new colours, a hex field) whose every change `TokenEditor` sets on the working copy at once, over Core's `ColorMath` (HSV, RGBA and `ColorValue` conversions), and the hex error text is Core's `ColorValue.NotAColour`.

    `Views/ThemeSettings/ThemePreview` is the right pane's mini window, drawn from `ThemeSettingsViewModel.PreviewTheme` (the working copy resolved for the half the open tab shows, null for an invalid theme) in its own resource dictionary filled by `ThemeBrushes`, so it follows unsaved edits while `ThemeBridge`, the page and the app keep the saved theme; a theme's own css is not previewed.

    The main and viewer windows open it from the title bar's ⋯ menu and Ctrl/Cmd+,; the dev harness also does, when `YAMV_DEV_HARNESS=1` and `YAMV_DEV_THEME_SETTINGS=1` (`App.CreateStartWindow`), and it refuses to start without `YAMV_DATA_DIR`.

## Integration Footguns

- A theme token rename or a new token also changes the page's `yamv.css` variables (`src/Yamv.App/Web/`) and the schema `themes/yamv-theme.schema.json`.
- A new `ThemeFileJson` field needs `ThemeFilePatch`'s `Apply` and `RootOrder` and `ThemeDefinition.ContentEquals` updated, or Save silently drops edits to it.
- `ThemeFolderWatcher` ignores the catalog's write-in-progress files by its own copy of `ThemeCatalog`'s temp-name pattern (`.<32 hex digits>.tmp`): a change to how the catalog names its temporary files changes both.
- `ThemeFolderWatcher.Dispose` waits for a `Changed` already running, and `ReleaseMainWindow` runs on the UI thread: `ThemeFolderSync`'s `Changed` handler may only post to the UI thread, never wait on it, or the dispose deadlocks.

  The sync is disposed before the settings writer and the bridge, so no posted reload reaches a disposed bridge. `SettingsWatcher` is the same: `App.OnSettingsFileChanged` only posts to the UI thread, and the watcher is disposed after the sync and before the writer (whose `WhenIdle()` it waits on) and the bridge.
- Theme colours are CSS hex, `#rrggbbaa`; Avalonia's `Color.Parse` reads 8 digits as `#aarrggbb`, so brushes are built from `ColorValue`'s R, G, B and A, never by parsing the hex.
- The page and the host speak by message name: `Web/yamv.js` posts `ready`, `rendered`, `scroll`, `link`, `key`, `find`, `drag`, `viewport`, `blocked` and `error`, which `DocumentView`'s message handler switches on, and the host calls the `window.yamv` functions `render`, `setTheme`, `setContentWidth`, `find`, `clearFind`, `openFind`, `scrollToId` and `setCardOpen`. A rename changes both sides, and the `RenderOptions` fields match the `settings.*` names the page reads.
- The `scroll` message is `{type:"scroll", value, line, offset, generation}`: `value` is the scroll fraction, `line` and `offset` the [scroll anchor](glossary.md) (`PageMessage.Line` and `Offset`, doubles, so a line that is not a whole number drops the anchor and keeps the message), and the page posts one after every render lands. `DocumentView` turns it into a `ScrollPosition(Fraction, ScrollAnchor?)` for `IDocumentSurface.ScrollChanged`; an offset outside 0 to 1 is clamped.
- The `drag` message is `{type:"drag", over:true|false}`, raised as `IDocumentSurface.DragOverChanged`. The page posts it on `dragenter`, `dragover` and `dragleave`, only for a drag of files from outside the page: its `dragleave` comes before the host popup's `DragEnter`, and after a drop the next drag starts with `dragover`, not `dragenter`.
- The `viewport` message is `{type:"viewport", value, generation}`, where `value` is the `clientWidth` of the content's parent, the width the text column is laid out in (WebView2 draws a classic 15 px scrollbar inside the document column on a tall document, so the column is wider than the page's text space). The page posts it after every finished render, always after that render's `rendered`, then again only when the width changes. `DocumentView` keeps it as `IDocumentSurface.ViewportWidth` (raising `ViewportWidthChanged`), clears it on every show and on adapter loss, and drops a report of another generation; `MainWindow` records the scrollbar inset (column less report) at each report and measures the pane as the live `DocumentColumn.Bounds.Width` less that inset, or the whole column while `ViewportWidth` is null, so a resize moves the measure before the page reports again.
- A file dropped on the page reaches WebView2 as `NewWindowRequested`, never as a navigation, one per file; `AllowExternalDrop = false` swallows every drop, so it is never set. Only the page's drag signal tells a drop from a document's own new-window link (`LinkDropRoute`), and the link is a drop only while the signal stands: up to 2 s, ended by the page's leave or the end of the drag. A drag begun in the page posts no signal.
- The host's drop popup becomes the OLE target about 25 ms after the page's signal, so the first drag events reach `MainWindow` and not the page; the overlay's grace (`DropOverlayViewModel`) covers the gap, and a drop on the popup is a `Drop` on the window, not a page link.
- The `link` message is `{type:"link", href, button, generation}`: `DocumentView` drops one whose `generation` is not the current render's, and the page swallows the second click of a double click so a link posts once.

  `window.yamv.scrollToId(id)` and `RenderOptions.Fragment` take an already decoded element id (`LinkPolicy` decodes it; the page decodes only the `#frag` of a document href it scrolls to itself), and `IDocumentSurface.ScrollToFragmentAsync(fragment)` calls `scrollToId` without a render.
- A link's fragment reaches the page only if `_state.Add` renders synchronously: `DocumentWindowViewModel.OpenLinkedDocument` leaves one pending-fragment slot tagged with the render generation that `_state.Add` starts, relying on the add running `OnStateChanged` → `RenderSelection` before it returns, and `RenderCoreAsync` passes the fragment on only for that generation. An add that renders later, or not at all, loses the fragment or sends it to a different render.
- `RenderOptions` carries `documentPath`, `anchorLine` and `anchorOffset` beside `scroll` and `fragment`.

  A `render` for the `documentPath` the page already shows is a reload: the page builds it in [staging](glossary.md) while the old page stays, then swaps it in at once, landing at the reader's place taken from the old page (its top or bottom [pin](glossary.md), else its top block found again by exact text, or a mermaid diagram by its source, then by `data-line`, then by scroll fraction) and ignoring `anchorLine`.

  A document short enough to fit in the view is at both ends, and the top pin wins, so a short file that grows stays at its top. Find keeps its query and the match at the same source position and never scrolls on a reselect.
- Any other `render` (a first show, a tab switch back, a session restore) goes to a fragment's element id if given, else `anchorOffset` of the way down the first block at or after `anchorLine`, else `scroll`.

  The anchor is saved per document in `session.json` as `scrollAnchors: { "<path>": { "line": 42, "offset": 0.35 } }`; `SessionStore.Normalize` repairs a missing map and drops an entry for a file not open, a negative line or an offset outside 0 to 1, and `SessionSnapshot.Build` takes the anchors as a required argument.
- `render`'s `contentWidth` option (`"760px"` or `"none"`, from `DocumentShow.ContentWidth`) is applied by the page only after it hides the outgoing document (`yamv-pending`), so the page shows once, at the new width; `setContentWidth` is for a live change while a document stays shown, and after a page reload `DocumentView` replays the latest width with the replayed render. `setCardOpen(open)` tells the page whether the confirm card is up: while it is, the page's keydown handler (`holdForCard`) default-prevents and stops Escape and Enter with any modifier and posts them as `key` (so the find bar's Escape does not close and a focused link is not clicked), and the flag is replayed to a reloaded page like the width.
- Core's renderer marks diagrams as `<pre class="mermaid">` and puts `data-line` (the zero-based source line) on every top-level block except front matter (`MarkdownRenderer.MarkSourceLines`); the page's diagram loader reads the `mermaid` class. Only those top-level blocks are scroll anchors: a `data-line` that raw HTML in the document carries is ignored, and a nested block is found through its parent.
- The web view swallows Ctrl/Cmd shortcuts while it has focus; the page forwards them as `key` messages (`KeyForwarded`), so a window shortcut is handled in both the window's tunnelled `KeyDown` and `KeyForwarded`, both through `MainWindow.RunShortcut`, which asks Core's `Shortcuts.Match` what the key means.

  The page forwards Ctrl/Cmd with the physical `BracketLeft` / `BracketRight` keys as `[` / `]` (no Shift, no Alt) whatever the layout prints there, and forwards no `[` / `]` typed from another key; AltGr typing is never forwarded.

  The page also forwards Ctrl/Cmd with `,` (the key's own name, `isShortcut` in `yamv.js`) for the theme settings shortcut.
- A theme or Appearance pick reaches `settings.json` through `ThemeBridge.RequestChanged` → `SettingsWriter.Request` (wired in `App.Shared`), not through the window; `session.json` holds neither (`SessionState` has no theme id or Appearance). The other way, a theme or Appearance read from an edited `settings.json` is applied with `RequestChanged` unsubscribed, never saved back.
- A change to any other field `DocumentWindowViewModel.BuildSession` reads (documents, selection, bounds, sidebar width) must reach `MainWindowSession` (through the view model's `SessionDirty` or a window event it follows), which hands a fresh `BuildSession` to `SessionSaver.Schedule`; a scroll (fraction and anchor) only calls `MarkDirty`, so it is written with the next save or the close. A change that reaches neither is saved only with the next unrelated change.
- The instance endpoint is derived from the lock file's full path (`InstanceEndpoint`): `main.sock` beside the lock on macOS and Linux, `yamv-` plus a hash of the user SID and the lock path on Windows. Moving `AppPaths.MainLockFile` moves the endpoint, so a build with the old path cannot reach a main running the new one.
- `InstanceCoordinator.StartServer`'s handler runs on a thread-pool thread: the App posts to the UI thread and never blocks in it (a `Dispose` from inside it never waits on the handler but still waits for the open connections, up to `DisposeWait`, before releasing the lock; a later concurrent `Dispose` from inside it returns at once, and from any other thread returns only after the lock is released).

  A request is carried out only after `InstanceRequest.TryBegin` succeeds, and the app then calls `Complete` at once; a request the launcher hung up on, the reply bound passed on or the server stopped under is abandoned and never begun. `activate` is a request like `open`: it is begun, answered once a window is forward, and abandoned the same way, so a launcher that hung up or timed out causes no late raise.
- The app's pid file is the lock path with the extension `.pid` (`main.lock` → `main.pid`), so it moves with `AppPaths.MainLockFile` too.

  `InstanceCoordinator` writes it right after taking the lock (a failure only warns) and `StopAnswering` or `Dispose` deletes it before releasing the lock, so the App must `Dispose` the coordinator on exit or a stale pid file is left; that is harmless, because `TryReadMainPid` returns the pid only when that process is running and its start time matches the recorded one. The start-time check holds on Windows and macOS; on Linux .NET computes start time per reader, so the read always gives null.

  The new main replaces the pid file by a move, which fails while the old file is still delete-pending (a FAT or network volume, or a reader that opened it without `FileShare.Delete`); after three attempts it warns, and a second launch then cannot bring the main window forward. Every reader of the pid file (`InstanceCoordinator.ReadPidFile`) opens it with `FileShare.Delete`.
- The app shuts down in a fixed order: the pid file is deleted and the server stopped (`InstanceCoordinator.StopAnswering`): begun in the background on the UI thread, on Windows when the last document window (main or viewer) closes, after the main window's `Closing` flush of the session and before its `Dispose` flush, else by `ReleaseMainWindow` if the app exits first (on macOS, which keeps running with no window, always at exit), and finished on the main thread by `Program.RunAsApp` after the UI loop ends, before the lock is released; the session saved, then the lock released (`Dispose`, which first closes every connection: on Unix the last server stream's close deletes the socket file, which must not happen after the next main has made its own).

  A second launch in between finds no pid and so waits up to 5 s for the lock (`SecondLaunch.LockWaitTimeout`, retrying every 100 ms through `TryAcquireMainLockQuietly`) and starts as the main instance; deleting the pid later than the server would let it bring forward a window that is closing. `StartServer` throws after `StopAnswering`.
- The launcher's request deadline (`SecondLaunch.RequestDeadline`) must stay below the server's reply bound (`InstanceCoordinator.ReplyBound`, a public `init` property, 10 s by default and validated positive; tests set it): past the bound a request the app has begun but not answered is closed with no reply, which the launcher reads as `closing` and sends again, so the files could open twice (an `activate` only raises a window again). A change to either needs the other.
- Every launch, with files or none, takes the lock in `Program` first; the one that gets it writes the pid file and starts the server before Avalonia starts, and a launch while the app runs sends `open` (files) or `activate` (none) instead of starting a process; the `activate` is held by the `UiReadyLatch` until the App opens the latch as the last step of `OnFrameworkInitializationCompleted`, then `App` un-minimises, shows and activates the main window on the UI thread (building it first when only viewers are open).

  Windows only lets a process bring a window forward when the foreground process allows it, so the second launch calls `AllowSetForegroundWindow(pid)` (`Platform/WindowsForeground`) before sending `activate`.
- On Windows, `File.Move(overwrite)` is refused while any other handle has the target open, so every multi-writer file in the data folder (`widths.json`) retries its replace.
- Fluent's window decoration parts are hidden by name in `App.axaml`: `PART_TitleTextPanel` by `Opacity` (its visibility is template-bound) and `PART_FullScreenButton` by `IsVisible` plus `Width=0` (`IsVisible` alone kept its layout slot). An Avalonia upgrade re-checks them with a `run-hidden.ps1 -App` capture.
- `Platform/WindowsFrame` copies how Avalonia sizes the main window's frame for an extended client area (`AdjustWindowRectExForDpi` with the shown window's style, the call its `WM_NCCALCSIZE` makes, with the top border zeroed), and `WindowPlacement.Fit` lands the window by it: an Avalonia upgrade that changes `WM_NCCALCSIZE` moves the fit. The 1 px outline is measured only at 96 dpi.
- A native view cannot be overlaid, so the window toggles `DocumentView`'s visibility for the empty, missing and can't-read states instead of drawing over it.
- The toast popup is a window of its own, and Avalonia's popup window answers `WM_NCHITTEST` for its whole rectangle, so outside its cards it would swallow clicks and the wheel meant for the document. `Platform/ToastClickThrough` subclasses that HWND (Windows only, attached by `MainWindow.OnToastPopupOpened`) and answers `HTTRANSPARENT` for a point on no card (`ToastHost.HasCardAt`), `HTCLIENT` on one.

  Avalonia makes a new popup window on each open, so the subclass is detached when the popup closes (`OnToastPopupClosed`) and attached again on the next open.
- `IFileActions.OpenConfirmed` is the only door that opens a type off the viewable list, and only the confirm card's Open reaches it: a new caller would let a link start a program or script without asking.
- `ThemeCatalog.LoadAll` can list two entries with one id (an invalid user file beside the built-in it shadows): look a theme up by id preferring the valid entry.
- The title bar's ⋯ menu shares one fill for hover and `:focus-visible`, and each open focuses its first item. That holds with one entry; a second entry needs the focus to follow the pointer or a distinct focus look, or two rows highlight at once.
