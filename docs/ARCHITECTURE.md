# YAMV — architecture

YAMV is a markdown viewer for Windows and macOS. `Yamv.Core` holds every piece of logic that can run without a UI (grouping, session, single-instance, rendering markdown to HTML); `Yamv.App` is the Avalonia 12 shell around a `NativeWebView`. Core references no UI framework. Terms are in the [glossary](glossary.md).

## Layers

- **`Yamv.Core`** (`src/Yamv.Core/`): owns grouping, git-root discovery, the session file, the single-instance lock and pipe, launch-argument parsing and markdown → HTML. References Markdig and the BCL only; never Avalonia.

  One main instance per user is held by a lock file (flock on Unix) plus a named pipe (a socket file on Unix) derived from the lock path, which later launches signal over; a named mutex is not used, because its behaviour differs on macOS.

  Session saving (`Session/`): `SessionSaver` writes `session.json` through `SessionStore` 500 ms after a change (a `Debouncer`, so two saves never run at once) and at once on `Flush`; a failed save is logged and retried by the next. `WindowPlacement` picks the screen (`ScreenArea`) a saved rectangle overlaps most, in physical pixels, and clamps the rectangle there; `WindowBounds.Scaling` is the screen scale it was saved at. `Input/Shortcuts` matches a key to a `ShortcutCommand` (Ctrl/Cmd+W, Ctrl+Tab, Ctrl+Shift+Tab, Ctrl/Cmd+B, Ctrl/Cmd+R).

  Theming (`Theming/`) parses theme files, resolves a theme for light or dark, builds its CSS (`ThemeCss`), and keeps the catalog of built-in and user themes (`ThemeCatalog`: list, import, inspect, duplicate, rename, save, delete); the editing services are `ThemeEditing` (set or reset a token, add a variant, rename), `ThemeTokenView` (the rows of one tab with value, layer and whether set there) and `ThemeFilePatch` (a save that edits only the changed values in the file's text).

  Deleting goes through `IFileTrash`, which the App implements with the Recycle Bin or Trash. `ThemeFolderWatcher` watches the user themes folder and raises `Changed` once per quiet 300 ms on a pool thread; a 2 s tick re-checks the folder, re-arms after an error and follows the folder being deleted or recreated. Theming owns no UI.

  Widths (`Widths/`) holds the content-width value (`ContentWidth`: px or Full, snapped to a 40 px grid) and `WidthStore`, the per-folder widths in `widths.json` shared by every instance: a lookup walks from the document's folder up to the file-system root, else the [app default](glossary.md); changes are replaced atomically and the store's lock is held through file IO, so callers keep changes off the UI thread.

  Startup (`Launch/`): `LaunchOptions.Parse` turns the command line into a `LaunchRequest`, and `StartupPlan.Decide` turns that into a `StartupAction` (print and exit, register, unregister, or start the app); `StartupPlan.FromResult`, `FromException` and `FromUnknownPath` turn a registration outcome into the line, stream, exit code and whether to notify the shell.

  Registration (`Registration/`, Windows only) writes and removes YAMV's [Open with registration](glossary.md) under the current user's `Software\Classes`, against an injectable root key so tests use a temporary subkey; it never takes over the default handler and removes only what it added.
- **`Yamv.App`** (`src/Yamv.App/`): owns windows, the tree, the document page (`Web/`, embedded as `Web/...` resources) and platform glue (macOS activation; `Platform/`). References Core.
  - `Program` carries out Core's `StartupPlan` before any window exists; `YAMV_DEV_HARNESS=1` skips it. `Platform/WindowsConsole` attaches the windowed `yamv.exe` to the parent's console (`AttachConsole`) before help, error or `--register` output is written, and `Platform/ShellNotify` tells Explorer that associations changed after a `--register` or `--unregister` that changed something.
  - `Controls/DocumentView` hosts the page in Avalonia's `NativeWebView`. The package's `WebResourceRequested` is observe-only and `NavigateToString` ignores its base URI, so `WebAssets` extracts the page to the [asset cache](glossary.md) and the page loads over `file://`. Two instances extracting at once race safely: the final folder only appears by renaming a complete staging copy.
  - The page's CSP is `script-src 'self'` with no inline script and no eval. Document HTML is inserted with `innerHTML` (so its scripts never run) after losing `style`, `style=`, `meta`, `base`, `link`, frames, objects and embeds; every image-like URL (`src`, `srcset`, `poster`, SVG `href`) must be http(s), a `data:image/` URL, or a host-less `file:` path inside the group root, so a document cannot reach a network share.
  - `Controls/IDocumentSurface` is the slice of `DocumentView` the window logic uses (show a document, theme CSS, content width, find, and the scroll, link and key events), so `ViewModels/DocumentWindowViewModel` and `Services/ThemeBridge` run against a fake in tests.

    The view model wraps Core's `DocumentWindowState`, renders the selection off the UI thread (a stale render is dropped by generation), keeps scroll per shown document, re-checks missing files every 2 s, and builds and restores the session.

    `ThemeBridge` picks the session's theme, sets the Avalonia theme variant, swaps one merged resource dictionary of chrome brushes (`YamvChromeBackground` … `YamvWarningLine`) and font (`YamvUiFont`, from Core's `ChromePalette`), and sends the theme CSS to every registered surface.
  - `Services/MainWindowFactory` composes the real main window: the log, the session, the theme catalog and bridge, `DocumentView`, `DocumentWindowState` and the view model.

    `Services/MainWindowSession` feeds the view model's `BuildSession` to a `SessionSaver` and schedules a save on the window's changes (documents, selection, collapsed groups, sidebar, position, size, maximized, sidebar width); `RestoreLayout` applies the saved placement and sidebar width (clamped 200-480) before the window shows.

    `Views/` holds `MainWindow` (custom title bar, `TitleBar`, and the tree sidebar on the right), `EmptyState` and `MissingDocumentPane`; `HarnessWindow` is the dev harness (the old document-view test window), opened instead of the main window when `YAMV_DEV_HARNESS=1`. `YAMV_DATA_DIR`, when set and not empty, is the data directory for the session, lock, logs and themes on every platform (`AppPaths.DataDirectoryVariable`).
  - `Views/ThemeSettingsWindow` is the theme settings window: the theme list (Built-in and Yours), the selected theme's header, an Appearance choice and a footer, over `ViewModels/ThemeSettingsViewModel` (the list, the selection and a working copy that edits change until Save or Revert; selecting a valid theme applies it, an invalid one only shows its errors) and `ThemeRowViewModel` (one row: chip colours, inline rename, whether Rename and Delete are on). The view model reaches the app only through `ThemeSettingsSeams` (apply a theme, the trash, Edit as text, the two confirms), so tests fake them. `Views/ThemeSettings/ConfirmDialog` is the in-window scrim dialog behind the unsaved-changes and delete confirms. Nothing in the main app opens the window yet; the dev harness does, when `YAMV_DEV_HARNESS=1` and `YAMV_DEV_THEME_SETTINGS=1` (`App.CreateStartWindow`), and it refuses to start without `YAMV_DATA_DIR`.
  - The find bar lives inside the page, because Avalonia cannot draw over a native web view (airspace). For the same reason an empty or missing state hides the web view rather than covering it.

## Integration Footguns

- A theme token rename or a new token also changes the page's `yamv.css` variables (`src/Yamv.App/Web/`) and the schema `themes/yamv-theme.schema.json`.
- A new `ThemeFileJson` field needs `ThemeFilePatch`'s `Apply` and `RootOrder` and `ThemeDefinition.ContentEquals` updated, or Save silently drops edits to it.
- `ThemeFolderWatcher` ignores the catalog's write-in-progress files by its own copy of `ThemeCatalog`'s temp-name pattern (`.<32 hex digits>.tmp`): a change to how the catalog names its temporary files changes both.
- Theme colours are CSS hex, `#rrggbbaa`; Avalonia's `Color.Parse` reads 8 digits as `#aarrggbb`, so brushes are built from `ColorValue`'s R, G, B and A, never by parsing the hex.
- The page and the host speak by message name: `Web/yamv.js` posts `ready`, `rendered`, `scroll`, `link`, `key`, `find`, `blocked` and `error`, which `DocumentView`'s message handler switches on, and the host calls the `window.yamv` functions `render`, `setTheme`, `setContentWidth`, `find`, `clearFind` and `openFind`. A rename changes both sides, and the `RenderOptions` fields match the `settings.*` names the page reads.
- Core's renderer marks diagrams as `<pre class="mermaid">` and puts `data-line` on the `code` element of a fenced block; the page's diagram loader and scroll restore read those.
- The web view swallows Ctrl/Cmd shortcuts while it has focus; the page forwards them as `key` messages (`KeyForwarded`), so a window shortcut is handled in both the window's tunnelled `KeyDown` and `KeyForwarded`, both through `MainWindow.RunShortcut`, which asks Core's `Shortcuts.Match` what the key means.
- A change to any field `DocumentWindowViewModel.BuildSession` reads (documents, selection, bounds, sidebar width, theme id and appearance) must reach `MainWindowSession` (through the view model's `SessionDirty` or a window event it follows), which hands a fresh `BuildSession` to `SessionSaver.Schedule`; a scroll only calls `MarkDirty`, so it is written with the next save or the close. A change that reaches neither is saved only with the next unrelated change.
- The instance endpoint is derived from the lock file's full path (`InstanceEndpoint`): `main.sock` beside the lock on macOS and Linux, `yamv-` plus a hash of the user SID and the lock path on Windows. Moving `AppPaths.MainLockFile` moves the endpoint, so a build with the old path cannot reach a main running the new one.
- `InstanceCoordinator.StartServer`'s handler runs on a thread-pool thread: the App posts to the UI thread and never blocks in it (a `Dispose` from inside it releases the lock and returns at once; any other concurrent `Dispose` returns only after the lock is released). `SignalAsync` returning true means the main instance read the frame on Windows, but only that the frame reached the socket's send buffer on Unix.
- The main-instance pid file is the lock path with the extension `.pid` (`main.lock` → `main.pid`), so it moves with `AppPaths.MainLockFile` too. `InstanceCoordinator` writes it right after taking the lock (a failure only warns) and `Dispose` deletes it before releasing the lock, so the App must `Dispose` the coordinator on exit or a stale pid file is left; that is harmless, because `TryReadMainPid` returns the pid only when that process is running and its start time matches the recorded one. The start-time check holds on Windows and macOS; on Linux .NET computes start time per reader, so the read always gives null.
- On Windows, `File.Move(overwrite)` is refused while any other handle has the target open, so every multi-writer file in the data folder (`widths.json`) retries its replace.
- Fluent's window decoration parts are hidden by name in `App.axaml`: `PART_TitleTextPanel` by `Opacity` (its visibility is template-bound) and `PART_FullScreenButton` by `IsVisible` plus `Width=0` (`IsVisible` alone kept its layout slot). An Avalonia upgrade re-checks them with a `run-hidden.ps1 -App` capture.
- A native view cannot be overlaid, so the window toggles `DocumentView`'s visibility for the empty and missing states instead of drawing over it.
- `ThemeCatalog.LoadAll` can list two entries with one id (an invalid user file beside the built-in it shadows): look a theme up by id preferring the valid entry.

## Test locations

- `tests/Yamv.Core.Tests`: everything in Core. A new Core type gets a test file at the mirrored path.
- `tests/Yamv.App.Tests`: App logic that needs Avalonia types (view model, `ThemeBridge`), run headless as plain `[Fact]`s through `HeadlessUnitTestSession` (`Avalonia.Headless.XUnit` fails discovery under xunit.v3). `Fakes/` holds the fake surface and log; `Yamv.App` exposes its internals to it. `Views/` holds headless window tests (title bar, tree, empty and missing states, shortcuts, `ThemeSettingsWindowTests`); `ViewModels/ThemeSettingsViewModelTests.cs` covers the theme settings view model over a temporary themes folder. `Services/` holds `ThemeBridgeTests`, `MainWindowSessionTests` (what is saved and when) and `MainWindowFactoryTests` (`RestoreLayout`).
- `tools/dev/page-check/`: a headless Chromium check of the document page (`npm install`, then `npm run check`), against a stubbed host.
- `tools/dev/run-hidden.ps1` with `tools/dev/capture-window.ps1`, both run under `tools/hidden-desktop.ps1`: screenshots of the real app off the owner's desktop, each run on a fresh data folder (`-App` for the main window, `-Session` to seed it, `-ThemeSettings` for the theme settings window, `-Themes` to seed its themes folder). `docs/design/fixtures/sample.md` is the sample document.
