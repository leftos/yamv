# YAMV — architecture

YAMV is a markdown viewer for Windows and macOS. `Yamv.Core` holds every piece of logic that can run without a UI (grouping, session, single-instance, rendering markdown to HTML); `Yamv.App` is the Avalonia 12 shell around a `NativeWebView`. Core references no UI framework. Terms are in the [glossary](glossary.md).

## Layers

- **`Yamv.Core`** (`src/Yamv.Core/`): owns grouping, git-root discovery, the session file, the single-instance lock and pipe, launch-argument parsing and markdown → HTML. References Markdig and the BCL only; never Avalonia.

  One main instance per user is held by a lock file (flock on Unix) plus a named pipe (a socket file on Unix) derived from the lock path, which later launches signal over; a named mutex is not used, because its behaviour differs on macOS.

  Session saving (`Session/`): `SessionSaver` writes `session.json` through `SessionStore` 500 ms after a change (a `Debouncer`, so two saves never run at once) and at once on `Flush`; a failed save is logged and retried by the next.

  `WindowPlacement` picks the screen (`ScreenArea`) a saved rectangle overlaps most, in physical pixels, and clamps the rectangle there; `WindowBounds.Scaling` is the screen scale it was saved at. `Input/Shortcuts` matches a key to a `ShortcutCommand` (Ctrl/Cmd+W, Ctrl+Tab, Ctrl+Shift+Tab, Ctrl/Cmd+B, Ctrl/Cmd+R, Ctrl/Cmd+O, Ctrl/Cmd+[ and ], which step the width narrower and wider).

  Documents (`Documents/`): `ReadFailure` turns an exception from reading a document into a reason (access denied for `UnauthorizedAccessException`, in use for an `IOException` whose `HResult & 0xFFFF` is 32 or 33, else a generic one) for the can't-read pane. `DocumentFileTypes` is the one list of in-app document types (`.md`, `.markdown`, `.mdx`, `.txt`; `Extensions`, `Patterns` for the pickers, `IsDocument`, case-insensitive), shared by the pickers, drag-drop and links.

  `DocumentFileWatcher` is [live reload](glossary.md)'s Core half: `SetPaths(documentPaths)` replaces the open documents (full paths, made canonical), and it raises `Changed` with a `DocumentsChangedEventArgs` of the open documents that may have changed, on a thread-pool thread, once the events naming an open document have been quiet for 150 ms or at most 1 s after the first. A subscriber posts to its UI thread and never waits on it there, since `Dispose` waits for a `Changed` already running; a subscriber that throws is logged. Each document window's view model subscribes through the App's `IDocumentChanges` seam (see Layers, App).

  Each folder of an open document is watched once, through the `IFolderEvents` and `IFolderProbe` seams of `Theming/FolderEvents.cs` that `ThemeFolderWatcher` shares. All work on a folder (probe, start and dispose its watch, read stamps) is that folder's pass on the thread pool, one pass per folder at a time, so a hung share delays no other folder; `SetPaths`, the 2 s tick and the watch's events only ask for a pass. Every 2 s a folder is probed: one that does not exist is watched once it does, and one deleted, recreated, replaced or whose watch reports an error is watched again, reporting every open document in it when it appeared, was replaced or the watch had worked before it failed.

  A folder whose watch cannot be started, or fails before it has worked for a full tick, is polled instead: every 2 s `FileStamps.Read` takes each open document's length and last write time (no document is opened), and only a document whose stamp changed since the previous poll is reported, so a rewrite that keeps both is missed. A document's first stamp is taken on a pass asked for when it is opened in a polled folder or the folder starts being polled; a change before that read is not reported. That window is one thread-pool dispatch (plus the rest of the folder's running pass), and, outside the watcher, the time between the subscriber's own read of the document and its call to `SetPaths`, so a subscriber reads a document and calls `SetPaths` close together (the [first-stamp window](glossary.md)).

  Links (`Links/`): `LinkPolicy.Decide(Uri?, LinkContext)` returns a `LinkDecision`: `OpenExternal(Uri)`, `OpenDocument(Path, Fragment)`, `OpenWithDefaultApp(Path)`, `Confirm(Path)` or `Ignore(Reason)`. `LinkContext` carries the `GroupRoot` and a `Resolve` function (`RealPath.Resolve` in production).

  `Decide` normalises the path with `Path.GetFullPath`, then ignores other schemes, `file:` with a host, UNC and device paths (before any file-system call), names with a character no file name may hold (on Windows including `:`, for alternate streams), unresolvable paths, missing non-documents and anything outside the group root (compared exactly on resolved paths). A [viewable type](glossary.md) opens with the default app only when both the link's name and its resolved target are on `LinkPolicy.ViewableExtensions`; a folder or any other type asks first (`Confirm`).

  `RealPath.Resolve` returns a `ResolvedPath?` (`Path`, `Exists`, `IsDirectory`), null when the path cannot be resolved safely. It follows links one hop at a time (at most 40, `MaxLinkHops`), never touches a UNC or device path, and returns long, on-disk-cased names. Nothing in the window calls `LinkPolicy` yet.

  Platform (`Platform/`): `RevealCommand` builds the Explorer or Finder process that reveals a path (a file selected, a folder opened, a missing path's nearest existing folder), BCL only so it is tested without a window. `OpenFileCommand.For(path, isMac)` builds the process that opens a fully qualified `.json` path with the system's association (the Windows shell open, or `/usr/bin/open` on macOS) and throws for any other path.

  Theming (`Theming/`) parses theme files, resolves a theme for light or dark, builds its CSS (`ThemeCss`), and keeps the catalog of built-in and user themes (`ThemeCatalog`: list, import, inspect, export, duplicate, rename, save, delete); the editing services are `ThemeEditing` (set or reset a token, add a half, rename), `ThemeTokenView` (the rows of one tab with value, layer and whether set there) and `ThemeFilePatch` (a save that edits only the changed values in the file's text).

  `ColorMath` and `Hsv` convert between HSV, RGBA and `ColorValue` for the colour picker; a grey keeps the hue the caller passes.

  Deleting goes through `IFileTrash`, which the App implements with `Platform/PlatformTrash` (the Windows Recycle Bin or the macOS Trash). `ThemeFolderWatcher` watches the user themes folder and raises `Changed` once per quiet 300 ms on a pool thread; a 2 s tick re-checks the folder, re-arms after an error and follows the folder being deleted or recreated. Theming owns no UI.

  Widths (`Widths/`) holds the content-width value (`ContentWidth`: px or Full, snapped to a 40 px grid; `TextSpace(paneWidth)` is the pane less the page's two 44 px side paddings, `SidePaddingPx` = 88, and every step compares against it). `WidthScopes.For` lists the popover's Saved for segments from a document, its group root and the width's source, without touching the file system, and carries the caption, Reset and Clear all rules (`InheritedFrom`, `CanReset`, `ClearAllRoot`) and whether a width set on the selected segment reaches the document (`Reaches`).

  `WidthStore` holds the per-folder widths in `AppPaths.WidthsFile` (`widths.json`) shared by every instance: a lookup (`Resolve` by document path, `ResolveFolder` by folder) walks from the document's folder up to the file-system root, else the [app default](glossary.md); `CountAtOrBelow(groupRoot)` counts the folders `ClearAtOrBelow` would remove; changes are replaced atomically and the store's lock is held through file IO, so callers keep changes off the UI thread.

  Settings (`Settings/`): `SettingsStore` holds the app-wide theme id and Appearance in `AppPaths.SettingsFile` (`settings.json`), shared by every process: `Load` reads the file again on each call and keeps the settings read before when it is missing, locked or unparseable, and `SetThemeId` and `SetAppearance` change a fresh read and replace the file in one move (a failure is logged and returns false; an unparseable file is first copied to `settings.json.bad`).

  `SettingsWriter` saves the picks off the caller's thread: `Request(themeId, appearance)` records the pair and returns with no file IO, one background write at a time saves the latest pair through the store (picks that arrive meanwhile coalesce into one more write, latest wins), and a failed write is logged and the next request writes again. `WhenIdle()` completes once every pair requested so far is written or failed; `Dispose` stops taking requests and waits up to 2 s.

  Startup (`Launch/`): `LaunchOptions.Parse(args, currentDirectory, directoryExists)` turns the command line into a `LaunchRequest` (a folder argument is an `InvalidLaunch`, "Not a file: {path}"; a nonexistent path is kept), and `StartupPlan.Decide` turns that into a `StartupAction` (print and exit, register, unregister, or `StartApplication(Files)`, where empty files mean a main launch); `StartupPlan.FromResult`, `FromException` and `FromUnknownPath` turn a registration outcome into the line, stream, exit code and whether to notify the shell.

  Second launch (`Launch/SecondLaunch`): `SecondLaunch.RunAsync` takes its effects as `SecondLaunchActions` (read pid, allow foreground, signal, bring forward, retry the lock, delay) and returns a `SecondLaunchOutcome`: `Activated` (exit 0), `Failed` (exit 1, whether or not the window could be brought forward) or `BecameMain` (the lock came free within `LockWaitTimeout`, so the caller starts as the main instance). The signal timeout is 1500 ms (`SignalTimeout`); `InstanceCoordinator.TryAcquireMainLockQuietly` reports a `MainLockAttempt`.

  macOS launch arbitration (`Launch/LaunchArbiter`): a state machine driven from the UI thread that turns framework, file-open and Dock or `activate` events into the windows to open. On a cold start main-window creation waits `GracePeriod` (300 ms) after framework initialization for launch-time file events, so a Finder-opened file starts only a viewer window; the arbiter keeps no timer, it asks the caller to start one (`StartGraceTimer`) and hear back through `GraceElapsed`. Inputs in an order it does not cover return `None` and never throw.

  Registration (`Registration/`, Windows only) writes and removes YAMV's [Open with registration](glossary.md) under the current user's `Software\Classes`, against an injectable root key so tests use a temporary subkey; it never takes over the default handler and removes only what it added.
- **`Yamv.App`** (`src/Yamv.App/`): owns windows, the tree, the document page (`Web/`, embedded as `Web/...` resources) and platform glue (macOS activation; `Platform/`). References Core.
  - `Program` carries out Core's `StartupPlan` before any window exists; `YAMV_DEV_HARNESS=1` skips it. `Platform/WindowsConsole` attaches the windowed `yamv.exe` to the parent's console (`AttachConsole`) before help, error or `--register` output is written, `Platform/WindowsForeground` allows a pid the foreground (`AllowSetForegroundWindow`) and brings that process's window forward (`ShowWindow`, `SetForegroundWindow`) for a second launch, and `Platform/ShellNotify` tells Explorer that associations changed after a `--register` or `--unregister` that changed something.
  - `Platform/PlatformTrash` is the `IFileTrash`: on Windows it moves a file to the Recycle Bin with `SHFileOperationW` (undo allowed), refuses any drive that is not a fixed disk because the shell would ask before destroying a file it cannot recycle, and refuses a 32-bit process; on macOS it calls `NSFileManager trashItemAtURL`. A failure throws and never hard-deletes. Nothing in the app calls it yet.
  - `Controls/DocumentView` hosts the page in Avalonia's `NativeWebView`. The package's `WebResourceRequested` is observe-only and `NavigateToString` ignores its base URI, so `WebAssets` extracts the page to the [asset cache](glossary.md) and the page loads over `file://`. Two instances extracting at once race safely: the final folder only appears by renaming a complete staging copy.
  - The page's CSP is `script-src 'self'` with no inline script and no eval. Document HTML is inserted with `innerHTML` (so its scripts never run) after losing `style`, `style=`, `meta`, `base`, `link`, frames, objects and embeds; every image-like URL (`src`, `srcset`, `poster`, SVG `href`) must be http(s), a `data:image/` URL, or a host-less `file:` path inside the group root, so a document cannot reach a network share.
  - `Controls/IDocumentSurface` is the slice of `DocumentView` the window logic uses (show a document, theme CSS, content width, find, and the scroll, link and key events), so `ViewModels/DocumentWindowViewModel` and `Services/ThemeBridge` run against a fake in tests.

    The view model is built from the state, the surface and `DocumentWindowServices` (the width store, the document reader, the clock and the log). It wraps Core's `DocumentWindowState`, renders the selection off the UI thread together with resolving its stored content width from the `WidthStore` (a stale render is dropped by generation; a store failure is logged and the document shows at the app default), shows it once through `ShowAsync(DocumentShow)` carrying that width, and `StepContentWidth` (Ctrl/Cmd+[ and ]) steps the width of the source the document inherits from, writes it and sends it live through `SetContentWidthAsync`, steps chained so two presses give two steps; a failed write is logged and the page keeps its width.

    The view model also keeps scroll per shown document, re-checks missing files every 2 s (the same tick retries the selected unreadable document, or a shown page kept while its file is in use, waiting while a read is still running; `SelectedIsUnreadable` and `UnreadableReason` drive the can't-read pane, from Core's `ReadFailure`, which maps a read exception to a reason), and builds and restores the session.

    Live reload in a window: `Services/IDocumentChanges` (`SetPaths`, `Changed`) is the seam over Core's `DocumentFileWatcher`, which `Services/DocumentChanges` wraps and tests replace with `Fakes/FakeDocumentChanges`. `MainWindowFactory` builds one per window, main or viewer, and hands it to the view model in `DocumentWindowServices.Changes` (null follows nothing); the view model owns and disposes it, and `SetPaths` is called with the open documents whenever that list changes, before a newly opened document is read. A report arrives on a pool thread and is only posted to the UI thread; there, the selected document is read and rendered again at its stored scroll, and every other reported document only has its missing flag re-checked (`DocumentWindowState.RefreshMissing(paths)`). A reload whose HTML and width equal those shown sends nothing to the page. Ctrl/Cmd+R is immediate: no grace, no in-use wait, and it always sends the page again.

    When a reload of the shown page finds its file gone, the page stays and the [grace](glossary.md) of 500 ms starts (`DocumentWindowState.ExistsOnDisk` asks without changing the missing flag; the tick starts it too); when it ends, the file is read once more and the page is shown if it is back, else the missing pane shows. A reload that finds the shown page's file in use keeps the page unchanged and reads again on the next report or tick, and the can't-read pane shows only after 10 s of it; a first show that fails shows its pane at once.

    `ThemeBridge` applies the theme and Appearance it is given (`Apply`; `App` gives it `settings.json`'s once at start), raises `RequestChanged` after an `Apply` that changed the requested theme id or Appearance, sets the Avalonia theme variant, swaps one merged resource dictionary of chrome brushes (`YamvChromeBackground` … `YamvWarningLine`) and font (`YamvUiFont`, from Core's `ChromePalette`), built by `Services/ThemeBrushes` (which also builds the brush and font of any one token, for the theme preview), and sends the theme CSS to every registered surface.

    `ThemeBridge.Reload()` (UI thread) re-reads the themes folder with `ThemeCatalog.LoadAll`: a changed valid file of the theme in use is applied to every window (brushes and page css), unchanged content does nothing, and a requested id that was missing and now appears is switched to. An invalid, deleted or renamed in-use file keeps its [last good version](glossary.md), including a user file that overrides a built-in id (the built-in does not replace it); Studio is used only for an id with no good version at all. An `Apply` of the kept id (a light or dark change) shows the last good version in the new appearance. `Reload` never raises `RequestChanged`, so `settings.json` is not rewritten; `ThemesReloaded` fires after every reload; one warning is logged per [bad streak](glossary.md) and one line when the file loads again.

    `Services/ThemeFolderSync` wraps Core's `ThemeFolderWatcher` for the user themes folder: its `Changed` handler (pool thread) only posts `ThemeBridge.Reload` to the UI thread and never waits on it, posted work after `Dispose` does nothing, a failed reload is logged, and its `Dispose` catches and logs the watcher's.
  - `Services/MainWindowFactory` composes the windows.

    `App` owns one `IAppLog` (`App.Log`), one `ThemeBridge` per process (`CreateBridge`, disposed at exit), one `SettingsStore` with one `SettingsWriter` and one `WidthStore`. On a normal start (never the dev harnesses) `CreateStartWindow` applies `settings.json` to the bridge once, subscribes `RequestChanged` to `SettingsWriter.Request`, and, for the main and viewer starts, creates one `ThemeFolderSync` (through the internal `CreateThemesSync` seam, one per process). `ReleaseMainWindow` disposes the sync, then the writer, then the bridge. It passes the log, bridge and width store to `Create` (the main window: the session, `DocumentView`, `DocumentWindowState` and the view model) and `CreateViewer`, neither of which applies a theme; the view model resolves each document's width from the store on the render thread, so a document opens at its stored width in either window. Every width change the view model makes (a Ctrl/Cmd+[ or ] step, the popover's save, Reset and Clear all) runs on one queue (`QueueWidthWork`), and `CreateContentWidthPopoverAsync` builds the `ContentWidthViewModel` behind it, which goes stale when the window's document changes.

    `CreateViewer` (a non-persisting window over `Program`'s files, handed over in the static `App.ViewerFiles`; an existing file is moved first so it is selected, and it reads no session).

    `MainWindowComposition` takes the document surface and a nullable `MainWindowSession` (null for a viewer) and unregisters the surface from the bridge on dispose.

    `Services/MainWindowSession` feeds the view model's `BuildSession` to a `SessionSaver` and schedules a save on the window's changes (documents, selection, collapsed groups, sidebar, position, size, maximized, sidebar width); `RestoreLayout` applies the saved placement and sidebar width (clamped 200-480) before the window shows.

    `Services/FileActions` holds `IFileActions` (the pickers, reveal, `OpenWithDefaultApp` and the clipboard; `AvaloniaFileActions` is the real one, with picker file types built from Core's `DocumentFileTypes.Patterns`, and takes `FileActionSeams` (the platform and a run-and-wait for a process; `FileActionSeams.Default` outside tests) as a required argument), which `MainWindow` uses for the tree menus, Ctrl/Cmd+O, Open files… and Locate…; tests replace it with `Fakes/FakeFileActions`. `OpenWithDefaultApp` opens a fully qualified `.json` path through Core's `OpenFileCommand`: on Windows the shell open is started and a refusal throws an `IOException`; on macOS `open` is waited for 2 s and a non-zero exit throws, while a run that outlives the wait is logged and left alone. Nothing in the app calls it yet.

    `Views/` holds `MainWindow` (custom title bar, `TitleBar`, and the tree sidebar on the right), `EmptyState`, `MissingDocumentPane` and `UnreadableDocumentPane`; `Views/ContentWidthPopover` is the content-width popover's content, shown in `MainWindow`'s native `Popup` anchored to the title bar's ⟷ button (the popup is a window of its own, so it sits over the web view, and `MainWindow` owns its dismissals); `HarnessWindow` is the dev harness (the old document-view test window), opened instead of the main window when `YAMV_DEV_HARNESS=1`. `YAMV_DEV_WIDTH_POPOVER` (`1`, `clearall` or `folder`, read only when `YAMV_DATA_DIR` is set; another value fails at start) has the main or viewer window open the popover once its first document shows. `YAMV_DATA_DIR`, when set and not empty, is the data directory for the session (`session.json`), widths (`widths.json`), settings (`settings.json`), lock, logs and themes on every platform (`AppPaths.DataDirectoryVariable`).
  - `Views/ThemeSettingsWindow` is the theme settings window: the theme list (Built-in and Yours), the selected theme's header, an Appearance choice and a footer, over `ViewModels/ThemeSettingsViewModel` (the list, the selection and a working copy that edits change until Save or Revert; selecting a valid theme applies it, an invalid one only shows its errors) and `ThemeRowViewModel` (one row: chip colours, inline rename, whether Rename and Delete are on).

    The view model reaches the app only through `ThemeSettingsSeams` (apply a theme, the trash, Edit as text, the two confirms, the Import and Export file pickers, and the Import notice's `ConfirmImport`), so tests fake them; Import and Export are on in the footer, and the dev harness answers `ConfirmImport` through the window. `Views/ThemeSettings/ConfirmDialog` is the in-window scrim dialog behind the unsaved-changes and delete confirms.

    `Views/ThemeSettings/ImportNoticeDialog` is the in-window scrim modal behind `ConfirmImport`, a card for the `ThemeInspection` (its `FilePath` is the path shown) with the css warnings; `ThemeSettingsWindow.ConfirmImportAsync` hosts it beside the confirm and disables everything behind it; a close cancels it (see `ConfirmCloseAsync` below). Its safe box uses `YamvCodeBackground`, a chrome brush because `codeBackground` is a chrome token in Core's `ChromePalette`.

    The view model's `ReloadFromDisk` and `KeepMine` commands and `ChangedOnDisk`, `DiskBroken` and `DiskError` drive the disk-change bar (`DiskBar` in `ThemeSettingsWindow.axaml`), and `ThemeRowViewModel.IsMissing` marks the greyed missing row the view model keeps for the theme in use whose file is gone ([look.md](design/look.md), [themes.md](design/themes.md)). `ThemeSettingsWindow.ConfirmCloseAsync` is the close check the window's own close and the app's shutdown wait on: it cancels an open Import notice or confirm, then asks the unsaved confirm (Save, Discard, Cancel) while the theme has unsaved edits.

    `Views/ThemeSettings/TokenEditor` is the token editor (a row per token, the Light/Dark/Shared tabs and the Add dark options strip), over `TokenRowViewModel` (one row's shown value, commit, reset and error) and the view model's token rows, tab state and `Hint`; a swatch raises `PickRequested` with `TokenPickEventArgs` and, on an editable row, opens `Views/ThemeSettings/ColorPickerPopup` (an overlay-layer Popup inside `TokenEditor`: saturation/value square, hue and alpha bars, old and new colours, a hex field) whose every change `TokenEditor` sets on the working copy at once, over Core's `ColorMath` (HSV, RGBA and `ColorValue` conversions), and the hex error text is Core's `ColorValue.NotAColour`.

    `Views/ThemeSettings/ThemePreview` is the right pane's mini window, drawn from `ThemeSettingsViewModel.PreviewTheme` (the working copy resolved for the half the open tab shows, null for an invalid theme) in its own resource dictionary filled by `ThemeBrushes`, so it follows unsaved edits while `ThemeBridge`, the page and the app keep the saved theme; a theme's own css is not previewed.

    Nothing in the main app opens the window yet; the dev harness does, when `YAMV_DEV_HARNESS=1` and `YAMV_DEV_THEME_SETTINGS=1` (`App.CreateStartWindow`), and it refuses to start without `YAMV_DATA_DIR`.
  - The find bar lives inside the page, because Avalonia cannot draw over a native web view (airspace). For the same reason an empty, missing or can't-read state hides the web view rather than covering it.

## Integration Footguns

- A theme token rename or a new token also changes the page's `yamv.css` variables (`src/Yamv.App/Web/`) and the schema `themes/yamv-theme.schema.json`.
- A new `ThemeFileJson` field needs `ThemeFilePatch`'s `Apply` and `RootOrder` and `ThemeDefinition.ContentEquals` updated, or Save silently drops edits to it.
- `ThemeFolderWatcher` ignores the catalog's write-in-progress files by its own copy of `ThemeCatalog`'s temp-name pattern (`.<32 hex digits>.tmp`): a change to how the catalog names its temporary files changes both.
- `ThemeFolderWatcher.Dispose` waits for a `Changed` already running, and `ReleaseMainWindow` runs on the UI thread: `ThemeFolderSync`'s `Changed` handler may only post to the UI thread, never wait on it, or the dispose deadlocks. The sync is disposed before the settings writer and the bridge, so no posted reload reaches a disposed bridge.
- Theme colours are CSS hex, `#rrggbbaa`; Avalonia's `Color.Parse` reads 8 digits as `#aarrggbb`, so brushes are built from `ColorValue`'s R, G, B and A, never by parsing the hex.
- The page and the host speak by message name: `Web/yamv.js` posts `ready`, `rendered`, `scroll`, `link`, `key`, `find`, `blocked` and `error`, which `DocumentView`'s message handler switches on, and the host calls the `window.yamv` functions `render`, `setTheme`, `setContentWidth`, `find`, `clearFind` and `openFind`. A rename changes both sides, and the `RenderOptions` fields match the `settings.*` names the page reads.
- `render`'s `contentWidth` option (`"760px"` or `"none"`, from `DocumentShow.ContentWidth`) is applied by the page only after it hides the outgoing document (`yamv-pending`), so the page shows once, at the new width; `setContentWidth` is for a live change while a document stays shown, and after a page reload `DocumentView` replays the latest width with the replayed render.
- Core's renderer marks diagrams as `<pre class="mermaid">` and puts `data-line` on the `code` element of a fenced block; the page's diagram loader reads the `mermaid` class. Scroll restore does not read `data-line`: the page reports and restores the scroll as a fraction (0 to 1) of the scrollable height, or scrolls to a fragment's element id when one is given.
- The web view swallows Ctrl/Cmd shortcuts while it has focus; the page forwards them as `key` messages (`KeyForwarded`), so a window shortcut is handled in both the window's tunnelled `KeyDown` and `KeyForwarded`, both through `MainWindow.RunShortcut`, which asks Core's `Shortcuts.Match` what the key means. The page forwards Ctrl/Cmd with the physical `BracketLeft` / `BracketRight` keys as `[` / `]` (no Shift, no Alt) whatever the layout prints there, and forwards no `[` / `]` typed from another key; AltGr typing is never forwarded.
- A theme or Appearance pick reaches `settings.json` through `ThemeBridge.RequestChanged` → `SettingsWriter.Request` (wired in `App.CreateStartWindow`), not through the window; `session.json` holds neither (`SessionState` has no theme id or Appearance).
- A change to any other field `DocumentWindowViewModel.BuildSession` reads (documents, selection, bounds, sidebar width) must reach `MainWindowSession` (through the view model's `SessionDirty` or a window event it follows), which hands a fresh `BuildSession` to `SessionSaver.Schedule`; a scroll only calls `MarkDirty`, so it is written with the next save or the close. A change that reaches neither is saved only with the next unrelated change.
- The instance endpoint is derived from the lock file's full path (`InstanceEndpoint`): `main.sock` beside the lock on macOS and Linux, `yamv-` plus a hash of the user SID and the lock path on Windows. Moving `AppPaths.MainLockFile` moves the endpoint, so a build with the old path cannot reach a main running the new one.
- `InstanceCoordinator.StartServer`'s handler runs on a thread-pool thread: the App posts to the UI thread and never blocks in it (a `Dispose` from inside it releases the lock and returns at once; any other concurrent `Dispose` returns only after the lock is released). `SignalAsync` returning true means the main instance read the frame on Windows, but only that the frame reached the socket's send buffer on Unix.
- The main-instance pid file is the lock path with the extension `.pid` (`main.lock` → `main.pid`), so it moves with `AppPaths.MainLockFile` too.

  `InstanceCoordinator` writes it right after taking the lock (a failure only warns) and `StopAnswering` or `Dispose` deletes it before releasing the lock, so the App must `Dispose` the coordinator on exit or a stale pid file is left; that is harmless, because `TryReadMainPid` returns the pid only when that process is running and its start time matches the recorded one. The start-time check holds on Windows and macOS; on Linux .NET computes start time per reader, so the read always gives null.

  The new main replaces the pid file by a move, which fails while the old file is still delete-pending (a FAT or network volume, or a reader that opened it without `FileShare.Delete`); after three attempts it warns, and a second launch then cannot bring the main window forward. Every reader of the pid file (`InstanceCoordinator.ReadPidFile`) opens it with `FileShare.Delete`.
- The main instance shuts down in a fixed order: the pid file is deleted, the server stopped (`InstanceCoordinator.StopAnswering`, run by `App` when the main window closes, or by `ReleaseMainWindow` if the app exits first), the session saved, then the lock released (`Dispose`). A second launch in between finds no pid and so waits up to 5 s for the lock (`SecondLaunch.LockWaitTimeout`, retrying every 100 ms through `TryAcquireMainLockQuietly`) and starts as the main instance; deleting the pid later than the server would let it bring forward a window that is closing. `StartServer` throws after `StopAnswering`.
- A main launch takes the lock, writes the pid file and starts the server in `Program` before Avalonia starts; the `activate` it sends waits in `ActivationGate` until the main window's `Opened`, then `App` un-minimises, shows and activates the window on the UI thread. Windows only lets a process bring a window forward when the foreground process allows it, so the second launch calls `AllowSetForegroundWindow(pid)` (`Platform/WindowsForeground`) before signalling.
- On Windows, `File.Move(overwrite)` is refused while any other handle has the target open, so every multi-writer file in the data folder (`widths.json`) retries its replace.
- Fluent's window decoration parts are hidden by name in `App.axaml`: `PART_TitleTextPanel` by `Opacity` (its visibility is template-bound) and `PART_FullScreenButton` by `IsVisible` plus `Width=0` (`IsVisible` alone kept its layout slot). An Avalonia upgrade re-checks them with a `run-hidden.ps1 -App` capture.
- A native view cannot be overlaid, so the window toggles `DocumentView`'s visibility for the empty, missing and can't-read states instead of drawing over it.
- `ThemeCatalog.LoadAll` can list two entries with one id (an invalid user file beside the built-in it shadows): look a theme up by id preferring the valid entry.
